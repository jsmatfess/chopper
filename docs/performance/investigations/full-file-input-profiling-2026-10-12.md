## Full-file input profiling (2026-10-12)

`chopper profile --config JOB` and **Analyze input** in both UIs now scan and validate every input record without applying operations, sorting/spilling rows, preparing CSV bytes, or publishing files. This intentionally replaces the proposed prefix preview: sorted or clustered input can hide entire groups until late in the source. Exact input row counts and full-file distinct statistics arrive independently of **Prepare exact outputs**. CLI `analyze` retains its previous exact-preparation semantics.

Statistics cover up to 64 columns (configured grouping/stratification columns first, then remaining columns) and requested multi-column key combinations. Small column value sets are counted exactly. Display sets retain at most 100 values per column and 256 KiB collectively; higher-cardinality counts use 1,024-register HyperLogLog sketches over the whole file. Estimates are labeled, with about 3.25% relative standard error; this is not a worst-case bound. Multi-column estimates hash length-delimited fields, preserving tuple boundaries. They describe distinct **input** keys, not final groups after arbitrary operation sequences. The first eight displayed records are only a visual sample; statistics do not use that sample. The [original HyperLogLog paper](https://dmtcs.episciences.org/3545/pdf) describes the estimator and small-range correction; this implementation uses 64-bit hashes.

The scan uses bounded parser/decoder buffers, up to 64 column sketches plus up to 64 operation-key sketches, the bounded display sets, and a 32 KiB row preview. It retains neither all rows nor an unbounded distinct-key catalog. Normal input codec/record limits still apply. Existing exact preparation also stops searching a display set after marking it incomplete, avoiding unnecessary tree lookups through the remainder of high-cardinality input.

The native server caches one completed profile. Its identity includes canonical path, length, modification/creation metadata, Unix file identity/change time where available, CSV settings, selected ZIP member, record limit, and codec memory ceiling. Changing seed, destination, compression, limits, worker count, or operations that use already-profiled columns/key combinations reuses statistics. A new multi-column combination or previously unprofiled column requires another full scan. A different input evicts the old entry before scanning; errors/cancellation never cache a partial profile. Metadata identity is a reuse heuristic, not a content proof. Exact preparation always rereads/validates the source and retains its own immutable snapshot.

The browser shares the profiling algorithm, explicitly invalidates on selection of a different File object, and retains the cache only within its current worker session. Starting exact preparation, cancellation, or completion can end that session. No profile cache is persisted across process/tab restarts. Profiling is optional, since profiling followed by preparation adds a read pass for a one-shot job. Source changes during the scan fail; late malformed records and corrupt compressed trailers are checked. Cancellation and progress are supported. Descriptive stage strategies are shown before preparation; these are not yet a calibrated planner or an input to automatic resource sizing.

### Measurements and CPU scaling

One million records, three columns, 32-byte repeated payload, seven keys sorted into consecutive blocks, about 42 MB source, 256 MiB working budget, 16 output chunks, fixed seed, local WSL/Linux storage with warm uncontrolled caches. Three repetitions alternate case order; no builds/browser tests overlap these measurements. All 24 published outputs passed fingerprints across workers and repetitions, including row order, stage statistics, filenames and manifest metadata. Three profiles saw all rows and all seven keys.

| Task | 1-worker preparation/profile | 1-worker complete job | 4-worker complete job |
| --- | ---: | ---: | ---: |
| Full-file input profile | 0.341 s | 0.344 s (profile only) | — |
| Plain chunks | 0.523 s | 0.626 s | 0.607 s |
| Partition → allocation | 1.478 s | 1.600 s | 1.543 s |
| Uniform shuffle | 1.630 s | 1.733 s | 1.618 s |
| gzip chunks | 0.516 s | 0.730 s | 0.591 s |

Profiling was 4.3× faster than partition/allocation preparation and 4.8× faster than shuffle preparation here. It is not equivalent work: exact preparation remains mandatory before publication. Going from one to four workers improved full shuffle time by about 7% and gzip by 19%. Streaming varied only a few percent despite having no parallel plain-output path. Aggregate process CPU time was near one CPU-second per wall-second on several pipelines; low total-machine CPU utilization does not by itself distinguish sequential computation from storage waits.

The existing native pool parallelizes run sorting and independent output compression. Parsing, stable routing, merge traversal, and plain publication remain sequential. Keep current defaults: simply increasing threads cannot accelerate those stages. Additional candidates, in order of practicality, are bounded batches of independent profiling/hash work, separately reserved independent group processing, and boundary-aware parallel parsing. Each needs complete-job benchmarks and explicit live-memory reservations first. Naive newline partitioning breaks quoted multiline CSV; parallel spill/merge/output on one device may add contention. Earlier read-ahead experiments in this document already demonstrate that extra concurrency can regress performance. No additional worker pipeline was introduced in this pass.

Reproduce with `python3 scripts/benchmark-profile.py --binary .tools/linux/target/release/chopper --rows 1000000 --repeats 3`. Use `--workers` and `--work-dir` for CPU/storage comparisons. [Raw measurements](../../evidence-originals.md#sha256-61f494cd7593c2c9969e0c94945c644a58920e4323900a4b11a06177ce8cd53a "Original: docs/benchmarks/full-profile-workers-2026-10-12.jsonl") include process CPU time, stage times, temporary writes and strategy counters. This narrow run does not calibrate broad storage classes, memory pressure, very wide input, or billion-row scale.

### GPU assessment

Decision: no GPU backend for the current engine. GPU CSV/grouping is technically possible: [libcudf exposes a GPU CSV reader](https://docs.rapids.ai/api/libcudf/stable/group__io__readers). But the present pipeline owns variable-length Rust strings, performs ordered external merges, and writes bounded CSV streams. GPU acceleration would require another representation and backend while preserving dialect, encoding, grouping and seeded-order semantics. There is no measured GPU result for this repository.

A useful future experiment would keep compact keys and payloads resident on a GPU across several compute-heavy operations, with a CPU fallback. Accelerating one small stage while transferring its data in and out may erase the benefit: [NVIDIA's best-practices guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#data-transfer-between-host-and-device) emphasizes minimizing host/device transfers. This is an architectural assessment, not a claim that GPUs cannot help large resident sorts. The current measurements support cheaper scans and existing bounded CPU parallelism first.
