What Auto does

  • For large outputs, compress 256 KiB blocks in bounded batches and assemble them in order. Each output is a normal gzip stream or ZIP member with its own CRC and lengths.
  • For prepared jobs with many outputs, use native file writers or hosted compression workers across eligible files. A large hosted member uses the workers within that member. Hosted publication now retires each large ZIP member’s temporary file before opening the next one. On the heavy hosted ZIP follow-up, completing one large member at a time changed median elapsed time from 13.30 to 13.28 seconds.
  • Use at most four workers per block batch. An explicit worker count limits concurrency. One worker requests serial compression. Available memory and hosted worker startup can reduce concurrency further.
  • Stream direct ZIP members into a private seekable archive and fill in their headers. Prepared ZIP can hold an admitted, small compressed member in memory and spill excess to a temporary file.
Auto eligibility

Direct Run uses the source size and configured byte cap. Parallel blocks are eligible when both allow at least 2 MiB. A source of at least 64 MiB can also use parallel blocks with a byte cap of at least 512 KiB. Explicit row caps keep limits-only compression serial.

Hosted prepared batches can use workers across files when the planned average is at least 256 KiB and members in the batch are under 2 MiB. The run must have sufficient workspace, browser worker capacity and successful worker startup. Larger members can use blocks within the file. The comparison calibrated 1 MiB caps and the tested size and pipeline controls.

The hosted UI shows peak parallel codec workers in the Auto details when used. Gzip and ZIP input and output remain supported. Existing Zstandard files need to be decompressed before import, and saved jobs using Zstandard output need a different codec.

How to read the results

Each repeated cell times three complete verified jobs per arm with alternating or rotated execution order. CLI timing ends at successful publication and process exit. Chromium timing ends at successful export and the completion marker. Input selection and independent verification are outside the clock. The benchmarks validate decoded byte order, row counts, names, file and byte caps, and manifests. The Partition → Balanced pipeline verifies order inside each region and its two child splits.

Measurements come from one Ryzen 7 5800X machine. The WSL CLI uses Linux ext4. The Windows CLI uses native NTFS. Bundled Chromium 156.0.8078.4 uses a disposable persistent profile and OPFS. Cache state is warm and uncontrolled. The fixtures are synthetic CSVs, so storage and timing results depend on compressibility, hardware and the rest of the job.

Startup and screening history

The first native screen accidentally selected one worker for streaming on both arms, and its timeout loop quantized the timer. The corrected native screen resolved workers at Run and used an enclosing runner timeout.

An early nested-worker prototype started inside synchronous WASI. It waited about 20 seconds before serial fallback, which produced valid outputs. The revised worker started before entering WASI. One 8 MiB smoke run per arm measured 0.610 to 0.343 seconds for gzip and 0.644 to 0.370 seconds for ZIP.

Input decompression

Streaming gzip and ZIP input stayed in Auto. From 256 MiB of decoded CSV to verified plain output, WSL medians were 0.86 seconds for plain input, 1.26 for gzip and 1.21 for a selected ZIP member. Four-thread Rapidgzip 0.16.2 with CRC verification followed by a normal Chopper run took 1.20 seconds end to end. It saved 0.06 seconds at the median of the pairs and lost one pair, while writing and rereading a 256 MiB decoded temporary input.

The experiment measured a decode-first workflow. A bounded parallel decoder integrated with Chopper would have a different timing and memory profile. The ZIP product selects one CSV member, and its existing streaming reader was used in the comparison. Rapidgzip documentation

Validation

The 428 verified benchmark samples include 348 comparison jobs and 80 diagnostic probes. The final host build passed 41 Chromium contracts and the 40-fixture execution graph suite. These include gzip and ZIP roundtrips with Auto, one worker and two workers, prepared file ordering, active compression cancellation, and checkable completion markers. The graph suite caught a stage ID that depended on the number of codec types. The UI now preserves the reserved category slots.

Default native workspaces passed 470 tests on WSL and 460 on native Windows. The WSL all-feature workspace passed 569 tests. The hosted production batch passed all 18 checks, both resource-contract variants passed, and the hosted UI passed 150 unit tests and 46 workspace tests. The restored production engine and worker assets matched the final hosted benchmark. The comparison used bundled Chromium and synthetic fixtures on a single machine. Installed browser release qualification, physical disk traffic and whole-browser RSS were outside that scope.

Source and evidence remain local. The private report is the only served artifact.
