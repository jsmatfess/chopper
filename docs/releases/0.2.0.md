# Chopper 0.2.0

When published, Windows and Linux CLI packages will be linked from the
[0.2.0 release page](https://github.com/jsmatfess/chopper/releases/tag/v0.2.0).
That page and its receipts are authoritative for final source identity, checksums,
validation and publication status; these notes do not establish them. The
[hosted app](https://chopper-1rx.pages.dev/) is deployed separately.
The [prior focused candidate review](0.2.0-review.md) retains only its original
source and artifact scope; it does not qualify the final release.

## Supported platforms

- Native 64-bit Windows and Linux: CLI only. There is no local server or native
  UI in this release scope. Exact executable
  targets, Linux runtime requirements and package hashes come from the final
  artifact receipt. Do not infer older-distribution compatibility from a source build.
- Hosted browser: separate WASI engine and static UI for supported desktop
  Chrome/Edge environments with the [required APIs and storage](../browser.md).
  Publishing native packages does not update the hosted app.
- macOS: source-only, with current release acceptance deferred. No macOS binary
  or runtime qualification is claimed. Mobile, Safari and Firefox are outside
  the selected hosted scope.

## Included scope

The release includes the complete current-main work and release cleanup, using
fresh native and hosted builds. It does not reuse the old focused639 packages.
The older candidate's exclusions of Guide and the hosted redesign are historical.

### Native CLI and data processing

- Ordered `chopper run --step` flags express pipelines directly; JSON Run remains
  available. `split` retains its fixed operation order. See the
  [Run reference](../run-cli.md) for settings, literal columns and shell quoting.
- Randomized execution uses internal entropy. There is no user-configurable seed
  or replay policy: remove `seed`, `random_seed` and `full_shuffle_policy` from
  older jobs. `--seed` and `--reproducible` are rejected. Preparing exact outputs
  still retains the encoded snapshot used by confirmation.
- Exact allocation, stable partition membership and strict serialized CSV caps
  remain contracts. Automatic execution never substitutes approximate allocation
  for exact assignment or weakens the requested shuffle distribution.
- Run can process limits-only jobs directly into private output; other pipelines
  prepare internally. Input profiling scans without preparing output, while
  explicit exact preparation retains CSV bytes and chunk boundaries.
- CSV, gzip, Zstandard and ZIP input/output follow the
  [format contract](../specification.md). Invalid decoding fails explicitly.
  Compressed-byte limits are advisory; strict CSV-byte limits include headers,
  quoting, encoding, BOM and line endings.
- Native publication protects existing destinations through atomic publication.
  Hosted export writes a completion marker after all files close; interrupted
  export can leave partial output without that marker.
- The hosted execution graph reports bounded observations of actual Run work.
  See [observation scope](../execution-observation.md); it is not a performance
  prediction or a full trace of every engine allocation.

`chopper guide [--config PATH]` provides the delivered terminal wizard for
capped, plain UTF-8 headered CSV exports: optional full-file inspection, resources,
atomic Job save/reload, save-and-exit and explicit Run confirmation. It requires
terminal stdin/stderr; stdout can capture Analysis JSON. Operations and broader
format/picker support in guided interaction remain future work; scripted Run
supports the full Job configuration. `split` remains a convenience command;
`analyze` performs exact preparation and `profile` scans without preparing output.
The [README](../../README.md) and [guided contract](../guided-cli-specification.md)
describe these capabilities and their limits.

### Redesigned hosted workspace and observed execution

The hosted UI includes the current workspace redesign, operation editing,
resource controls, theme behavior and native command/configuration export.
**Run in CLI** generates ordered Run commands for the current draft with
platform-specific quoting and literal column/group selectors; larger commands
fall back to JSON export.

Graph, List and Timeline share step selection and inspection. They show actual
input, preparation, grouping, shuffle, allocation, split, spill/merge, compression,
export and completion-marker work within fixed observation bounds. Counts, row
visits and bytes keep distinct units; measured work, activity windows and job
elapsed time are not interchangeable. Missing measurements remain unknown.

Step diagrams animate observed active work, pause between parent attempts and
resume without restarting. Aggregate steps remain In Progress until an
authoritative finalization or processing barrier; gaps between groups do not
fabricate completion. Timeline uses worker-observed timing, freezes at completion
or interruption and labels an unobserved end. Hidden tabs pause visual refresh
while retaining facts. The graph describes data flow, not parallel execution.

Statistics and results retain their input/configuration origin. Parser/source
changes invalidate unrelated pending results; late polls and retired worker
messages cannot overwrite newer lifecycle state. Prepared confirmation uses its
captured snapshot and destination. Run history survives form edits and worker
shutdown until replaced by a new Run. Cancellation, cleanup, interrupted work and
late same-Run confirmations retain separate status/publication boundaries.
See the [observation contract](../execution-observation.md) and
[result ownership contract](../browser.md#result-ownership-and-publication-contracts).

### Memory controls and performance work

Numeric working-memory budgets and explicit `auto`, worker selection, temporary
space, record and file limits remain available. Hosted manual working memory now
accepts up to 2048 MiB, while omitted and automatic defaults remain at most
256 MiB. Its per-instance tracked ledger is 1 GiB and its linear-memory ceiling
is 2 GiB; none is a total browser RSS cap.

Included engine improvements cover admitted CSV spans and quoting, validated
compact-field traversal, fixed-size spool keys and buffered short-field copies,
buffered bounded random draws, exact shuffle/partition fusion, shuffled-parent
allocation ranges, and eligible redundant-shuffle elision. They preserve strict
CSV validation, exact quotas, ordering barriers and snapshot confirmation.
Native CLI JSON decoding, streamed CLI JSON, encoding selection preservation
and pinned dependency license notices are also included. Native HTTP/server
changes and native-picker acceptance described in older records are historical
and are not part of the 0.2 product or release claims.

The [performance registry](../performance-overview.md) links each decision to its
recorded workloads, runtimes and limitations. These are scoped improvements,
not a general speed guarantee. Surviving experimental features remain opt-in;
rejected experiments and their evidence remain historical. The final fresh
release requires its own matching validation and artifact records.

## Limits and acceptance

Omitted working memory remains 256 MiB; automatic sizing is explicit. Engine
reservations are working-allocation accounting, not a complete process/RSS cap.
The hosted engine is single-threaded, has a 2 GiB linear-memory ceiling and uses
private browser storage for output and intermediates before export. Destination
capacity and browser quota remain independent limits.

[Validation](../validation.md) records scoped Linux/native Windows, installed
Chrome/Edge, scale and failure/cancellation checks for particular builds. Existing
10 GB native and 1 GB browser acceptance records belong to the prior selected
candidate. They do not establish arbitrary-input, complete RSS, device-fault,
macOS or final-source acceptance. No general billion-row certification or
universal performance improvement is claimed.
